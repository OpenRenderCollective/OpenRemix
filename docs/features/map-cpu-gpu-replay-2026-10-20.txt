Controlled static map CPU/GPU replay comparison (2026-10-20)

Purpose and conditions
Check whether the recent draw-constant/scratch changes improve representative
static-map execution, rather than extrapolating isolated packing benchmarks.
Baseline: forwardplus-balanced-cubemap-fit-v1. Current: native d612a22, including
655ee74 draw constants, ecf1ed9 draw scratch and shared GGX filter terms. The GGX
change does not execute in these warm-cache steady-state windows.
The wrapper diagnostic host now exports .host.csv (aa9c1e4), with CPU attempt
identities and separate wall/record/fence/setup breakdowns. It rejects duplicate
completed snapshots and queries which straddle a CPU attempt change. Older runtimes
without these APIs keep GPU-only measurements. The two existing replay settings
and GPU timing-window tests pass; ten actual replay launches validate the CSV path.
No installed game DLL is changed by this diagnostic-tool checkpoint.

1920x1080 render/output, MSAA4, frozen animation, manual exposure1, surface budget
4M texels, 1024 atlas pages, 256 samples, 3 bounces, 16 cubemaps at face size32,
full-scale SSR, no live RT GI/reflections, shared replacement-mod directory.
Default replay first-spawn camera/FOV65 is fixed per map. No viewmodel, engine
entities, particles, UI or material proxies are present. This is not the live
GMod workload or a benchmark of every shipped quality setting.

For each map: current-build cold cache seed, then old/new/new/old warm-cache
controls. Every timed control reports a cache hit, the same bake identity and
identical published content hashes. 1024 distinct completed GPU frames follow
at least128 warmup frames and3 warmup seconds. CPU rows are filtered by readiness,
backend, bake hash and the GPU report's host observation interval. Every control
has1024 unique completed CPU rows in that interval. CPU/GPU rows are not paired
as exact frames; GPU queries are delayed. CPU setup can include handoff/waiting.
No sum of nested phases is presented as render-thread CPU computation.
